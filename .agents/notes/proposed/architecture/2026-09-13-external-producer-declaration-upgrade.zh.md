# Agent Note：外部 Session 事件生产者的声明升级通道

Status: proposed

[English](2026-09-13-external-producer-declaration-upgrade.md) | 中文

相关已实现合同：[外部 Session 事件生产者的持久声明](../../implemented/architecture/2026-08-29-durable-external-session-event-producers.zh.md)

## 问题

持久声明的首版合同把每个 Session 对同一 producer 固定在**一条精确声明**上：追加时，日志中既有的同 producer 声明必须与写入 handle 的三元组（producer、version、eventTypes）完全一致，否则抛出冲突错误。读取侧同样要求每个持久声明都有完全一致的活跃注册。

该决策保住了 v1 的全部目标——持久词汇身份、失败关闭读取、无静默语义丢失——但它同时意味着：**受信插件一旦以新版本（新事件词汇）发行，它自己旧版本创建的所有 Session 就被永久写冻结**。新 Session 从首次写入起声明新版本，不受影响；旧 Session 的任何状态变更写入都会失败。由于外部产品的 Session Log 就是其唯一持久事实源（需求、运行、保留现场、授权都活在里面），这不只是兼容性不便，而是把升级变成了"放弃全部进行中工作"。

该边界已被真实使用击中。一个外部产品在插件升级后对其既有 Session 的第一次状态写入被拒绝：

```text
Error: session "session-…" has a conflicting declaration for external producer "dsh-pactflow"
```

读取（经只读兼容注册）完全正常，写入没有可用通道；宿主与插件均不存在声明升级机制。v1 Agent Note 明确把"schema 驱动迁移"与"兼容版本范围"排除在首版之外，但没有排除**声明显式升级**本身——本提案补上这一通道，并保持 v1 的失败关闭不变量不变。

## 决策

### 同 producer 的声明序列，单调升版

把"每个 Session 每 producer 恰一条声明"推广为"**按位置排序的声明序列**"。对同一 producer，后续声明事件必须满足：

1. **严格升版**：新 version 在 semver 意义下严格大于该 producer 在本 Session 中的全部既有声明版本。降版或同版不同集合仍是硬冲突，错误与现在一致。
2. **词汇超集**：新 `eventTypes` 必须包含被取代声明的全部事件类型。词汇只增不减；任何位置上每个事件类型仍然只有一个所有者，`assertEventsSupported` 的逐位置准入逻辑无需引入"所有权消失"概念。
3. **经新版本 handle 触发**：升级不是独立的核心 API。持有更高版本注册的受信插件照常调用 `handle.append()`；追加器发现日志中该 producer 的最新声明可被当前 handle 取代时，**同步地**先追加新声明事件、再追加目标事件——与 v1 首次声明写入的两追加结构完全相同，中间无异步间隙。核心只负责结构校验、单调性校验与追加顺序；信任边界与 v1 一致（受信 Host 插件写，核心验证）。

等价声明（同版同集合）维持现状：复用既有声明，不重复写。

### 读取准入按段生效

`PersistenceCoordinator.assertEventsSupported()` 把"单个活跃声明"推广为"**每个 producer 一条有序声明序列**"：

- 对每个持久声明，注册表中必须存在**完全一致的活跃注册**（与 v1 的 `requireReadable` 逐条相同；只读兼容注册满足此要求）。缺任何一个仍以 `SessionFormatUnsupportedError` 失败，诊断包含生产者与版本。
- 每条声明从其所在位置起准入自己的事件类型；声明之前出现其类型的外部事件仍然被拒绝。
- 后缀读取的前缀回退规则不变：声明位于返回范围之外时先读完整前缀再判定。

这不需要新事件类型、不改变 envelope 或 `SESSION_FORMAT_VERSION`：升级只是再写一条 v1 已有的 `session/external-event-producer` 事件。更旧的 DSH 构建遇到多声明日志会按现有未知/不支持规则失败关闭，方向正确。

### 插件侧义务（外部生产者合同）

- 为每个**其 Session 仍需可读**的历史三元组保留活跃的只读兼容注册，并对每个历史元组维护冷 fold 测试——这两点都是 v1 已有的义务，本提案不新增。
- 写入侧仍只持有一个当前版本 handle；升级语义由核心在追加时执行，插件不做日志改写、不做多版本并行写。

## 已考虑的替代方案

**修改 Session Header 或 envelope 加版本标签。** 再次否决，理由与 v1 相同：Header 不可变，envelope 变化会无必要地触发格式版本迁移；声明段语义已提供所需的按段解释。

**允许任意重声明（无单调性、无超集要求）。** 否决：降版与词汇回退会让"这份日志当前需要什么解释"变成位置相关的猜谜；单调升版 + 超集使解释确定性保持平凡。

**读取时跳过缺少注册的历史声明。** v1 已否决"生产者缺失时跳过事件"，本提案不重新打开：静默跳过正是声明制度要消灭的语义丢失。

**产品侧自愈（fork 持久化、双写新 Session、复制迁移）。** 否决：等价于 v1 否决过的"在每个外部产品中 patch 持久化协调器"——分叉信任边界、破坏 Profile 可移植性，并制造第二事实源。

**把升级做成独立核心命令/API。** 否决：额外授权面与调用时序问题，且受信插件的追加路径已经携带了全部所需信息；v1 的"handle 是唯一受支持写入路径"原则不需要第二个入口。

## 测试

- 核心单元：升级合法性矩阵（升版+超集通过；降版、同版异集合、词汇缩缺、跨 producer 争用全部拒绝）；多声明日志的结构校验与规范排序。
- 追加合同：升级写入 = 声明事件 + 目标事件两次同步追加；等价声明不重复写；校验失败保持日志不变；二次升级、升级后再等价追加均正确。
- JSONL 与 SQLite 冷读取：含两次升级的日志在"全部历史注册在位"时完整还原；任一历史注册缺失时以 `SessionFormatUnsupportedError` 失败且诊断指名 producer/version；第一方事件与无外部声明的 Session 字节兼容不变。
- 后缀读取：声明在范围外时回退前缀，判定与完整读取一致（含多声明）。
- 既有 v1 测试全部保持通过；`pnpm run verify-persistence-catalog`、`pnpm run test:docs`、`pnpm run doc-sync` 与 lint 通过；生成的持久化目录与 Session 文档同步更新。

## 后果

- 读取一份可能含升级的日志，要求**其用过的每个版本**的注册都在场（含只读兼容注册）。注册表占用随发行版本数增长；这是"读取成功即完整还原"不变量的直接代价。
- 词汇只增约束意味着外部事件类型一旦发行就不能从后续声明中撤回；类型退役需要产品自行保证不再写入，并保留声明以便读取历史段。
- 插件降级到低于 Session 最高声明版本且未带历史只读注册时，该 Session 不可读——与 v1 同方向的失败关闭，但升级通道使这种状态更容易出现，诊断必须指名缺失的具体三元组。
- 升级写入与 v1 首次声明相同，是两次同步追加；observer 与 handle 的预校验义务不变。
